### Pattern 2: Nuclear Drizzle Metadata Regeneration
**What:** Delete all migration artifacts and regenerate from current schema
**When to use:** When journal/snapshots are inconsistent with SQL files and current schema
**Steps:**
1. Back up `drizzle/` directory (already in git)
2. Delete `drizzle/meta/` directory contents
3. Delete `drizzle/*.sql` files
4. Run `npx drizzle-kit generate` — creates single fresh migration + metadata
5. Verify generated migration matches current schema
6. Run existing tests to confirm nothing is broken

### Pattern 3: Drizzle-kit Generate for Fresh Start
**What:** Running `drizzle-kit generate` with no snapshots creates a single initial migration
**When to use:** After wiping metadata, to get clean state
**Example command:**
```bash
npx drizzle-kit generate
```
This reads `lib/schema.ts` and the `drizzle.config.ts`, generates:
- `drizzle/0000_<random_name>.sql` — single migration with all CREATE TABLE statements
- `drizzle/meta/0000_snapshot.json` — snapshot reflecting current schema
- `drizzle/meta/_journal.json` — single entry referencing the snapshot

### Anti-Patterns to Avoid
- **Manual JSON editing of snapshots:** Drizzle snapshot JSON has auto-generated UUIDs (`id`, `prevId`) that must link correctly across entries. Manual editing is fragile and error-prone [VERIFIED: inspected 0004_snapshot.json structure]
- **Keeping inconsistent metadata:** Only 5 journal entries for 7 SQL files, and entry #4 has the wrong tag — this will cause `drizzle-kit migrate` and `drizzle-kit generate` to malfunction [VERIFIED: inspected _journal.json]
- **Partial test coverage:** Only replacing `it.todo` on line 4 but leaving other `it.todo` entries — the CONTEXT says to replace line 4 specifically, but adding a negative "no email" assertion is important regression protection

## Common Pitfalls

### Pitfall 1: Drizzle-kit generate creates duplicate migration
**What goes wrong:** Running `drizzle-kit generate` without clearing existing snapshots will compare current schema against the latest (stale) snapshot and try to generate增量 migrations for changes already applied via SQL files 0005 and 0006. This creates a 0007 migration that duplicates existing applied changes.
**Why it happens:** The 0004 snapshot still has `muvekkil.email` and `taraf` without driver fields. Drizzle-kit sees a diff between that snapshot and current schema.
**How to avoid:** Must delete all `drizzle/` contents before regenerating. Running `drizzle-kit generate` on an empty directory creates a fresh single migration.
**Warning signs:** `drizzle-kit generate` outputting "2 changes" or creating migration files numbered 0005+ when they should not exist.

### Pitfall 2: Wrong journal tag mapping
**What goes wrong:** The current `_journal.json` entry idx 4 has `tag: "0004_drop_muvekkil_email"` but the actual SQL file is `0004_add_dilekce_sablonu.sql`. This mismatch means drizzle-kit cannot correctly track which migration has been applied.
**Why it happens:** Phase 10 manually created entries in the journal but misaligned tags with SQL file names.
**How to avoid:** Nuclear regeneration eliminates this entire class of problem — fresh journal and snapshot are auto-generated by drizzle-kit.

### Pitfall 3: Test assertion ambiguity on email column
**What goes wrong:** Only asserting `expect(muvekkil).toHaveProperty('id')` etc. (positive assertions) doesn't prevent someone from re-adding `email`. A future developer might add `email` back and all positive checks would still pass.
**Why it happens:** Positive tests don't protect against field addition, only deletion.
**How to avoid:** Include an explicit negative assertion: `expect(muvekkil).not.toHaveProperty('email')`.
**Warning signs:** Test file only has `expect(table).toHaveProperty(...)` without any `not.toHaveProperty(...)` for removed fields.

### Pitfall 4: DB migration tracking table inconsistency
**What goes wrong:** After nuclear regeneration, the `__drizzle_migrations` table in SQLite may have entries for old migration file hashes. Running `drizzle-kit migrate` with new migrations could try to re-apply or skip incorrectly.
**Why it happens:** Drizzle Kit tracks applied migrations by hash in `__drizzle_migrations` table.
**How to avoid:** After regeneration, either (a) clear the `__drizzle_migrations` table before running `drizzle-kit migrate`, or (b) since the DB is already in the correct state, simply don't run `drizzle-kit migrate` — just verify the schema matches.
**Warning signs:** `drizzle-kit migrate` throwing "migration already applied" or "hash mismatch" errors.

### Pitfall 5: CONTEXT.md D-02 vs nuclear approach conflict
**What goes wrong:** D-02 says "Keep existing 7 SQL migration files as-is" but the nuclear approach deletes them. Following D-02 literally leads to error-prone manual metadata editing.
**Why it happens:** `drizzle-kit generate` cannot regenerate snapshots for existing SQL files — it creates new ones from schema diff. There's no "just fix the metadata from existing SQL" command.
**How to avoid:** Resolve the conflict: the 7 SQL files are already preserved in git history. Regenerating creates a clean baseline. Git commit history retains the incremental migration history for reference.
**Warning signs:** Attempting to manually create 5+ snapshot JSON files and 7 journal entries by hand.
