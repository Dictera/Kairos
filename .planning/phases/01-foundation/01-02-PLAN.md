# Plan 01-02: SQLite + Drizzle ORM

## Goal

Create the SQLite connection singleton with WAL mode and required pragmas, define the minimal proof-of-concept schema stub, configure drizzle-kit, run the generate+migrate workflow, and verify the database file is created at `./data/db.sqlite`.

## Context

Depends on Plan 01-01 (package.json, next.config.ts, .env.local must exist).

Critical decisions from CONTEXT.md:
- **D-06:** Minimal schema stubs only — one `schema_test` table to prove generate+migrate works
- **D-07:** Phase 2 owns all real entity schemas — no entity structure in this plan

Critical pitfalls from RESEARCH.md:
- WAL pragma MUST be set on the Database instance directly (not in migration SQL — cannot run inside transactions)
- Use `globalThis` singleton pattern to prevent multiple connections during Next.js hot reload
- `better-sqlite3` is Node-only — `lib/db.ts` must only be imported from server components and route handlers
- Use `generate` + `migrate` workflow — NEVER `drizzle-kit push`

**[BLOCKING]:** The schema migration task (`npx drizzle-kit generate` → `npx drizzle-kit migrate`) must run after schema files are created and before verification. This plan cannot pass without the database file existing at `./data/db.sqlite`.

## Security Threat Model (ASVS L1)

### Applicable ASVS Categories
- ASVS 8.3 — Sensitive Private Data: SQLite file contains all case data — must not be served publicly
- ASVS 14.1 — Build: Native module must not be bundled by client-side toolchain

### Threats & Mitigations

| Threat | STRIDE | Mitigation |
|--------|--------|------------|
| `lib/db.ts` imported into a client component, exposing SQLite path/data | Information Disclosure | `lib/db.ts` must have `import 'server-only'` at top (or be verified to only be imported in server contexts); Next.js `serverExternalPackages` prevents bundling |
| `data/db.sqlite` accidentally committed to git | Information Disclosure | `.gitignore` entry `data/db.sqlite` enforced in Plan 01-01; verify it exists |
| `drizzle-kit push` used instead of `generate`+`migrate`, losing migration history | Tampering | Only `npm run db:generate` and `npm run db:migrate` are used; `push` is not in package.json scripts |
| Multiple concurrent SQLite writers causing SQLITE_BUSY | Denial of Service | `globalThis` singleton prevents multiple connection instances; `busy_timeout = 5000` gives 5s retry window |
</threat_model>

**lib/db.ts:**
```typescript
import Database from 'better-sqlite3'
import { drizzle } from 'drizzle-orm/better-sqlite3'
import * as schema from './schema'

// globalThis singleton prevents multiple SQLite connections during Next.js hot reload.
// Each reload re-executes this module but reuses the existing connection.
const globalForDb = globalThis as unknown as {
  db: ReturnType<typeof drizzle<typeof schema>> | undefined
}

function createDb() {
  const sqlite = new Database('./data/db.sqlite')
  // WAL mode: must be set on instance, NOT in migration SQL (cannot run in transactions)
  sqlite.pragma('journal_mode = WAL')
  // busy_timeout: wait up to 5s when another writer holds the lock
  sqlite.pragma('busy_timeout = 5000')
  // foreign_keys: enforce FK constraints (SQLite disables them by default)
  sqlite.pragma('foreign_keys = ON')
  return drizzle({ client: sqlite, schema })
}

export const db = globalForDb.db ?? (globalForDb.db = createDb())
```

Note: Do NOT add `import 'server-only'` here if the `server-only` package is not installed — it would cause an import error. Instead, document the server-only constraint in a comment. If `server-only` is available (it ships with Next.js), add it at the top.
